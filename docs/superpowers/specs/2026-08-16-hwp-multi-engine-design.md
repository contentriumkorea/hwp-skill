# hwp-skill 다중 엔진 문서 조판 및 무창 실행 설계서

작성일: 2026-08-16

상태: 사용자 방향 승인, 상세 설계 검토 대기

대상 저장소: `hwp-skill`
적용 대상: 차기 주요 버전

## 1. 문서 지위

이 문서는 기존 `2026-08-16-hwp-skill-design.md`의 안전 원칙과 원본 보존 정책을
유지하면서, 다음 전제를 대체한다.

- 한컴오피스 COM 자동화를 기본 문서 처리 엔진으로 사용한다.
- 한컴오피스가 없으면 HWP/HWT 작성과 편집을 지원하지 않는다.
- `Visible=false`를 설정한 현재 사용자 세션의 한컴 자동화를 무창 실행으로 본다.
- 새 문서 디자인은 한컴 명령을 순서대로 호출해 작성한다.

차기 버전은 한컴오피스를 선택형 검증 엔진으로만 취급한다. 기본 경로는 문서
패키지와 바이너리를 직접 읽고 쓰는 무창 엔진이다.

## 2. 목표

Codex의 Documents 스킬이 DOCX를 만드는 것과 같은 원리를 HWP/HWPX에 적용한다.

1. 사용자의 자연어 요청을 내용 구조와 디자인 규칙이 포함된 문서 설계도로 바꾼다.
2. 표, 이미지, 제목, 본문, 강조 상자, 머리말과 꼬리말을 실제 문서 요소로 조판한다.
3. 한컴오피스가 없는 컴퓨터에서도 HWPX를 직접 읽고, 만들고, 수정한다.
4. 검증된 독립 엔진을 통해 일반적인 HWP를 직접 읽고, 만들고, 수정한다.
5. 한컴오피스가 설치되어 있어도 기본 작업에서는 한컴 GUI를 실행하지 않는다.
6. 사용자가 다른 프로그램에서 계속 작업해도 창 노출, 포커스 이동, 작업표시줄
   깜빡임 또는 결과 파일 자동 열림이 없어야 한다.
7. 가능한 환경에서는 결과를 페이지 이미지로 렌더링하고, 모든 페이지를 검사한 뒤
   반복 보정한다.
8. 실제 렌더링을 하지 못한 환경에서는 구조 검증과 예측 미리보기를 실제 화면 검증과
   구분해 보고한다.
9. 기존 1~8번 기능군인 읽기, 제작, 구조 편집, 공공문서 자동화, 자연어 편집, 검토,
   일괄 처리 및 시각 검증을 유지한다.

## 3. 비목표

- 암호, DRM, 배포용 문서 제한 또는 전자서명 우회
- 문서 매크로 또는 능동 OLE 개체 실행
- 지원하지 않는 바이너리 레코드를 임의로 재작성
- 렌더러가 없는 환경에서 한컴과 픽셀 단위로 동일하다고 주장
- 사용자 동의 없는 외부 문서 업로드
- 현재 사용자의 화면에서 한컴을 잠깐 실행한 뒤 숨기는 방식을 무창 처리로 인정
- 모든 한컴 전용 개체를 첫 버전부터 완전히 편집

## 4. 검토한 접근법

### 4.1 한컴 자동화 전용

장점은 한컴이 이해하는 기능을 그대로 사용할 수 있다는 점이다. 그러나 한컴이 없는
컴퓨터에서 작동하지 않고, COM 객체 생성 직후 GUI 창이 생겨 `Visible=false` 적용
전에 포커스를 가져갈 수 있다. 현재 사용자 세션에서 실행하는 한 이상 창 노출이 전혀
없다고 보장할 수 없으므로 기본 구조로 사용하지 않는다.

### 4.2 모든 문서를 HWPX로 변환

HWPX는 ZIP/XML 기반 공개 형식이므로 읽고 쓰기 쉽다. 하지만 기존 HWP를 먼저 HWPX로
변환하려면 별도 변환 엔진이 필요하고, 최종 HWP 재생성도 해결해야 한다. 불필요한
왕복 변환은 알 수 없는 개체와 서식의 손실 가능성을 높이므로 모든 작업에 강제하지
않는다.

### 4.3 선택한 방식: 기능 기반 다중 엔진

파일 형식, 요청 작업, 설치 환경, 문서 복잡도와 검증 요구를 사전 점검한 뒤 가장
안전한 엔진을 자동 선택한다.

- HWPX는 ZIP/XML을 직접 처리한다.
- HWP/HWT는 검증된 독립 바이너리 엔진으로 직접 처리한다.
- 한컴 네이티브 엔진은 현재 사용자 화면과 분리된 실행 환경에서만 선택적으로 쓴다.
- 지원하지 않는 기능은 GUI 방식으로 몰래 전환하지 않고 `BLOCKED` 또는 제한된
  결과로 보고한다.

## 5. Documents 스킬에서 가져올 원리

DOCX 품질은 Word 창을 자동 조작해서 나오는 것이 아니다. 문서 내용을 구조화하고,
정확한 디자인 수치를 적용해 파일 패키지를 직접 만든 뒤, 페이지 이미지로 렌더링해
반복 검사하는 데서 나온다. HWP 스킬도 다음 네 단계를 동일하게 갖는다.

### 5.1 의미 구조

문서를 단순 문자열이 아니라 제목, 문단, 목록, 표, 이미지, 캡션, 참고 상자,
머리말과 꼬리말 같은 의미 단위로 구성한다.

### 5.2 디자인 토큰

페이지, 여백, 글꼴, 글자 크기, 색상, 문단 간격, 줄 간격, 표 너비, 셀 여백,
테두리와 이미지 배치 값을 문서 작성 전에 수치로 확정한다. 프로그램 기본값이나
렌더러별 자동 맞춤에 의존하지 않는다.

### 5.3 직접 파일 생성

HWPX에서는 XML 요소, 관계, 이미지 데이터와 매니페스트를 직접 만든다. HWP에서는
독립 바이너리 작성 엔진의 객체 모델을 사용한다. 한컴 창에서 키 입력을 재현하지
않는다.

### 5.4 렌더링 반복 검사

작성 결과를 PDF와 페이지별 PNG로 만들고, 모든 페이지에서 잘림, 겹침, 빈 페이지,
표 폭, 이미지 위치, 글꼴 대체와 페이지 흐름을 확인한다. 수정 후에는 다시 렌더링한다.

## 6. 전체 구조

```text
사용자 요청
  → Skill Router
  → 환경·파일·작업 사전 점검
  → DocumentSpec 또는 PatchPlan 생성·검증
  → Backend Router
       ├─ HWPX Direct Backend
       ├─ HWP Portable Backend
       └─ Isolated Hancom Backend
  → 임시 결과 작성
  → 구조·의미·원본 보존 검증
  → 사용 가능한 Renderer 선택
  → PDF·페이지 PNG 생성 및 전 페이지 검사
  → 검증 결과에 따라 최종 파일 승격 또는 격리
```

### 6.1 새 문서와 기존 문서의 차이

새 문서는 `DocumentSpec`을 단일 설계 원본으로 사용한다. 기존 문서는 파일 전체를
공통 모델로 변환해 다시 만들지 않고, `PatchPlan`으로 원본 구조에 필요한 변경만
적용한다. 이 구분은 기존 문서의 알 수 없는 레코드와 개체를 최대한 보존하기 위해
필수다.

## 7. 공통 문서 설계도

`DocumentSpec`은 내용과 디자인을 함께 기록한다.

```json
{
  "version": "2.0",
  "documentType": "public-report",
  "outputFormat": "hwpx",
  "page": {
    "size": "A4",
    "orientation": "portrait",
    "marginsMm": { "top": 18, "right": 18, "bottom": 18, "left": 18 }
  },
  "theme": "public-report-blue",
  "blocks": [
    { "type": "title", "text": "사업 추진 계획" },
    { "type": "lead-callout", "label": "핵심", "text": "요약 내용" },
    { "type": "heading", "level": 1, "text": "1. 추진 배경" },
    { "type": "paragraph", "text": "본문 내용" }
  ]
}
```

### 7.1 기본 블록

- `cover`, `title`, `subtitle`, `metadata`
- `heading`, `paragraph`, `quote`
- `numbered-list`, `bullet-list`, `checklist`
- `lead-callout`, `note-box`, `warning-box`
- `table`, `form-grid`
- `image`, `figure`, `caption`
- `page-break`, `section-break`
- `header`, `footer`, `page-number`
- `footnote`, `endnote`, `bookmark`, `hyperlink`, `toc`

### 7.2 디자인 프리셋

첫 디자인 팩은 다음 문서 유형을 제공한다.

- `public-report`: 공공기관 보고서와 계획서
- `official-letter`: 공문
- `proposal`: 사업·제작 제안서
- `storyboard`: 영상 스토리보드
- `meeting-minutes`: 회의록
- `compact-guide`: 매뉴얼과 체크리스트
- `clean-document`: 세련된 일반 문서

각 프리셋은 페이지 규격, 제목 계층, 본문 리듬, 표 스타일, 강조 상자, 머리말과
꼬리말을 하나의 토큰 묶음으로 정의한다. 서로 다른 프리셋의 값을 한 문서에서
임의로 섞지 않는다.

### 7.3 조판 규칙

- 표는 전체 폭, 들여쓰기, 열별 폭과 셀 여백을 명시한다.
- 열 너비는 내용 길이에 따라 배분하고 동일 너비를 기본으로 삼지 않는다.
- 행 높이는 원칙적으로 자동 확장하며 고정 높이로 글자를 자르지 않는다.
- 긴 표에는 반복 머리행을 설정한다.
- 이미지 비율을 보존하고 페이지의 실제 사용 가능 폭을 넘지 않는다.
- 캡션과 이미지를 가능한 한 같은 페이지에 둔다.
- 제목만 페이지 아래에 남지 않도록 다음 문단과 묶는다.
- 한글 글꼴의 존재 여부와 대체 결과를 사전 점검한다.
- 재배포 가능한 한글 글꼴을 제공할 경우 파일과 라이선스를 별도 관리한다.

## 8. 처리 엔진

### 8.1 HWPX Direct Backend

한컴 설치 여부와 운영체제에 관계없이 HWPX ZIP/XML을 직접 읽고 쓴다.

담당 범위:

- 패키지와 매니페스트 검증
- 본문, 문단, 글자 모양과 문단 모양
- 표, 셀, 행, 열, 병합 정보
- 이미지와 `BinData` 관계
- 구역, 용지, 여백, 머리말, 꼬리말과 쪽 번호
- 필드, 책갈피, 하이퍼링크, 각주와 미주
- 새 문서 작성과 지원 범위 내 기존 문서 부분 수정

ZIP 경로 탈출, 외부 XML 개체, 비정상 압축 비율과 과도한 해제 크기를 계속
차단한다.

### 8.2 HWP Portable Backend

한컴이 없는 환경에서 HWP 바이너리를 읽고 쓰는 어댑터다. 공개 API는 특정
라이브러리에 종속되지 않게 정의한다.

후보 선택 원칙:

1. HWP 읽기와 저장을 실제로 지원해야 한다.
2. 원본을 변경하지 않는 왕복 저장 시험을 통과해야 한다.
3. 한글, 표, 이미지, 필드와 서식에 대한 골든 문서 시험을 통과해야 한다.
4. 암호 문서와 알 수 없는 레코드를 안전하게 거부하거나 보존해야 한다.
5. 라이선스가 공개 저장소와 상업적 사용에 적합해야 한다.
6. Codex 환경에서 별도 GUI 없이 재현 가능하게 설치돼야 한다.

1차 후보는 성숙한 Java `hwplib`를 기준 구현으로 삼고, 순수 JavaScript
`hwplib-js`를 배포용 후보로 비교한다. JavaScript 후보가 골든 문서와 차등 시험을
통과하면 설치가 간단한 기본 엔진으로 채택하고, 그렇지 않으면 자체 포함 Java
런타임 또는 사용 가능한 Java를 활용하는 방식을 선택한다. `openhwp`는 HWP 읽기와
HWPX 변환·렌더링 보조 가능성을 평가하되 HWP 바이너리 쓰기가 검증되기 전에는
유일한 결과 엔진으로 사용하지 않는다.

### 8.3 Isolated Hancom Backend

한컴 전용 개체, 실제 한컴 렌더링 또는 최종 HWP 호환성 확인이 필요한 경우에만
사용한다. 현재 사용자의 대화형 데스크톱에서는 실행하지 않는다.

허용 환경:

- 별도 Windows 사용자 세션
- 로컬 가상머신
- 사용자가 관리하는 사내 한컴 작업기
- 명시적으로 구성된 비공개 렌더링 노드

Windows 서비스의 세션 0에서 한컴 GUI 자동화가 안정적으로 동작한다고 가정하지
않는다. 별도 대화형 세션이나 가상머신에서 작업자를 실행하고 결과 파일과 검증
보고서만 현재 Codex 세션으로 돌려준다.

## 9. 기능 기반 라우팅

| 입력·요청 | 기본 엔진 | 한컴 없는 환경 | 처리 원칙 |
|---|---|---:|---|
| HWPX 읽기 | HWPX Direct | 지원 | XML 직접 검사 |
| HWPX 새 문서 | HWPX Direct | 지원 | `DocumentSpec` 조판 |
| HWPX 편집 | HWPX Direct | 지원 | 원본 패키지 부분 수정 |
| 일반 HWP 읽기 | HWP Portable | 지원 | 변환 없이 직접 읽기 |
| 일반 HWP 새 문서 | HWP Portable | 지원 | 빈 문서 또는 조판 결과 작성 |
| 일반 HWP 편집 | HWP Portable | 조건부 지원 | 무변경 왕복 시험 후 적용 |
| 복잡한 HWP 편집 | Isolated Hancom | 격리 작업기 필요 | 없으면 안전하게 차단 |
| HWT 기반 생성 | Portable 또는 Isolated | 엔진 지원 범위 내 | 양식 원본 보존 |
| 실제 한컴 화면 검증 | Isolated Hancom | 격리 작업기 필요 | 현재 화면 실행 금지 |
| 암호·DRM·서명 문서 | 없음 | 미지원 | 우회 없이 `BLOCKED` |

라우터는 엔진을 선택한 이유, 사용하지 않은 엔진과 제한 사항을 결과 보고서에
기록한다. 엔진 실패 후 현재 사용자 화면의 GUI로 자동 전환하지 않는다.

## 10. 완전 무창 실행 정책

### 10.1 기본 모드

기본 실행 모드는 `silent`다. 이 모드에서는 다음 조건을 모두 지킨다.

- 현재 사용자 세션에서 `Hwp.exe`를 시작하지 않는다.
- COM 객체를 생성한 뒤 숨기는 방식을 사용하지 않는다.
- Word, 한컴, 파일 탐색기 또는 결과 파일을 자동으로 열지 않는다.
- 하위 프로세스는 콘솔 창 없이 실행한다.
- 포그라운드 창과 키보드 포커스를 변경하지 않는다.
- 작업표시줄에 새 창 또는 주의 표시를 만들지 않는다.
- 알림은 Codex 안의 작업 결과로만 제공한다.
- CPU와 디스크 집약 작업은 가능한 범위에서 백그라운드 우선순위로 실행한다.

### 10.2 실행 모드

- `silent`: 직접 파일 엔진과 진짜 헤드리스 도구만 허용한다. 기본값이다.
- `isolated-native`: 현재 화면과 분리된 한컴 작업자가 구성됐을 때만 허용한다.
- `interactive`: 사용자가 현재 요청에서 한컴 창 실행을 명시한 경우에만 허용한다.

`silent` 작업이 지원 범위를 벗어나면 `interactive`로 자동 승격하지 않는다.
`isolated-native` 작업자가 없으면 필요한 기능과 미완료 검증을 설명하고 멈춘다.

### 10.3 무창 수용 시험

동일 작업을 반복 실행하면서 다음을 자동 측정한다.

- 실행 전후 포그라운드 창 핸들이 동일하다.
- 현재 대화형 세션에 새 HWP 프로세스가 없다.
- 현재 데스크톱에 스킬 소유의 보이는 최상위 창이 없다.
- 테스트 중 다른 프로그램의 연속 타이핑 입력이 중단되지 않는다.
- 결과 파일 연결 프로그램이 자동 실행되지 않는다.
- 실패·재시도·시간 초과 경로에서도 위 조건이 유지된다.

릴리스 수용 시험은 대표 읽기, 새 문서 작성, 이미지 포함 작성, 편집, 일괄 처리와
검증 작업을 각각 반복한다. 단 한 번이라도 포커스 탈취나 창 노출이 확인되면
`silent` 릴리스를 실패로 판정한다.

## 11. 렌더링과 시각 검증

### 11.1 렌더러 계층

1. `native`: 격리된 한컴에서 만든 PDF와 PNG. 실제 한컴 화면 검증에 사용한다.
2. `compatible`: GUI 없이 동작하는 호환 렌더러 결과. 지원 범위를 기록한다.
3. `preview`: 동일 `DocumentSpec`을 HTML/PDF로 조판한 예측 미리보기다.
4. `none`: 구조·의미 검사만 수행한 상태다.

예측 미리보기는 디자인 의도를 빠르게 확인하기 위한 것이며 실제 HWP/HWPX 렌더링
통과로 간주하지 않는다.

### 11.2 결과 등급

- `VISUAL_NATIVE_PASS`: 격리된 한컴 결과의 모든 페이지를 확인함
- `VISUAL_COMPATIBLE_PASS`: 호환 렌더러의 모든 페이지를 확인함
- `VISUAL_PREVIEW_ONLY`: 공통 설계도 기반 미리보기만 확인함
- `STRUCTURAL_ONLY`: 렌더링 없이 구조와 내용만 확인함

기존 `PASS`, `PASS_WITH_WARNINGS`, `BLOCKED`, `FAILED` 상태와 별도로 시각 등급을
기록해 내용 성공과 화면 검증을 섞지 않는다.

요청한 `requireVisualLevel`을 충족하지 못하면 최상위 결과를 단순 `PASS`로
표시하지 않는다. 시각 검증이 선택 사항이면 `PASS_WITH_WARNINGS`, 납품 필수
조건이면 최종 승격을 중단하고 `BLOCKED`로 기록한다.

### 11.3 전 페이지 검사

렌더링이 가능한 경우 다음을 모두 검사한다.

- 페이지 수와 빈 페이지
- 글자·표·이미지 잘림과 겹침
- 제목 계층과 문단 간격
- 표 너비, 셀 여백, 반복 머리행과 페이지 분할
- 이미지 비율, 캡션과 본문 사이 간격
- 머리말, 꼬리말과 쪽 번호
- 누락 글꼴과 대체 글꼴
- 원본 편집의 경우 페이지별 시각 차이

레이아웃에 영향을 주는 수정 뒤에는 반드시 다시 렌더링한다.

## 12. 기존 문서 보존

1. 실제 형식, 크기, 수정 시각과 SHA-256을 기록한다.
2. 읽기 전용 검사와 보호 상태 검사를 수행한다.
3. 기존 HWP를 독립 엔진으로 편집할 때 먼저 무변경 왕복 저장 시험을 수행한다.
4. 알 수 없는 레코드나 손실 가능성이 발견되면 편집을 차단하거나 격리 엔진으로
   전환한다.
5. 원본은 덮어쓰지 않고 임시 결과에만 변경한다.
6. 결과를 다시 열어 본문, 표, 이미지, 필드, 구역과 관계를 재검사한다.
7. 검증 통과 후에만 최종 결과 파일로 원자적으로 승격한다.
8. 원본 SHA-256이 작업 전후 동일한지 확인한다.

기존 HWP를 항상 HWPX나 공통 JSON 모델로 완전 변환한 뒤 재생성하지 않는다.
지원하지 않는 데이터는 가능한 경우 불투명 데이터로 보존하고, 보존을 증명할 수
없으면 수정하지 않는다.

## 13. 명령과 보고서

공용 실행기의 차기 인터페이스는 다음 개념을 제공한다.

- `capabilities`: 설치 환경과 엔진별 지원 기능 출력
- `inspect`: 파일 형식에 맞는 직접 엔진으로 읽기
- `compose`: `DocumentSpec`으로 새 HWP/HWPX 작성
- `validate-plan`: 기존 `PatchPlan` 검증
- `apply`: 원본 보존 편집
- `batch`: 파일별 라우팅을 포함한 미리보기와 실행
- `compare`: 의미·구조·시각 비교
- `render`: 사용 가능한 렌더러로 페이지 이미지 생성
- `verify`: 재열기, 구조, 내용과 시각 등급 종합

주요 선택값:

- `executionMode`: `silent`, `isolated-native`, `interactive`
- `outputFormat`: `hwp`, `hwpx`
- `designPreset`: 디자인 팩 이름
- `renderer`: `auto`, `native`, `compatible`, `preview`, `none`
- `requireVisualLevel`: 납품에 필요한 최소 시각 등급

보고서에는 입력·출력 경로, 원본 해시, 선택 엔진, 선택 이유, 실행 모드, 렌더러,
시각 등급, 지원하지 않은 기능, 경고와 복구 방법을 포함한다.

## 14. 오류 처리

다음 상황에서는 수정 전에 `BLOCKED`로 끝낸다.

- 실제 파일 형식과 확장자가 다름
- 보호·암호·DRM·서명 상태를 안전하게 처리할 수 없음
- 요청 작업을 지원하는 직접 엔진이나 격리 작업자가 없음
- 기존 문서의 무변경 왕복 저장이 구조 손실을 일으킴
- 수정 대상이 없거나 둘 이상이라 모호함
- 필요한 글꼴 또는 외부 자산이 없어 사용자가 요구한 디자인을 유지할 수 없음
- `silent` 모드인데 작업이 GUI 실행을 요구함

엔진 오류, 저장 오류 또는 검증 실패가 발생하면 임시 결과를 완성본으로 승격하지
않는다. GUI 실행, 자동 클릭 또는 현재 사용자 세션의 한컴 실행으로 우회하지 않는다.

## 15. 시험 우선 개발

실제 스킬과 코드를 수정하기 전에 현재 버전의 실패를 재현하는 시험부터 추가한다.

### 15.1 RED 기준선

- 한컴이 없는 환경에서 현재 `preflight`가 `BLOCKED`되는지 확인한다.
- 현재 HWPX 새 문서와 편집 요청이 지원되지 않는지 확인한다.
- 현재 한컴 COM 생성이 `Visible=false` 설정 전에 GUI 프로세스를 만들 수 있음을
  현재 세션의 프로세스와 창 이벤트로 포착한다.
- 현재 빈 문서 생성 계획으로는 Documents 스킬 수준의 디자인 토큰, 구성요소와
  시각 등급을 표현할 수 없음을 계약 시험으로 확인한다.
- 일반적인 “한글 문서 파일로 작성해줘” 요청에서 스킬 검색 설명이 충분히
  트리거되는지 기준선을 기록한다.

### 15.2 GREEN 구현 순서

1. 엔진 기능 선언과 라우터 계약
2. `silent` 기본 정책과 GUI 자동 전환 금지
3. HWPX 직접 읽기·쓰기
4. `DocumentSpec`과 디자인 프리셋
5. 독립 HWP 엔진 어댑터
6. 구조·의미 검증과 무변경 왕복 시험
7. 렌더러 어댑터와 시각 등급
8. 격리형 한컴 작업자
9. 스킬 문서, 설치기와 공개 안내

각 단계는 실패하는 시험을 먼저 확인하고 최소 구현으로 통과시킨 뒤 정리한다.

### 15.3 시험 묶음

- 단위 시험: 라우팅, 스키마, 디자인 토큰과 안전 정책
- 패키지 시험: HWPX ZIP/XML, 관계, 이미지와 매니페스트
- 골든 문서 시험: 한글 본문, 표, 이미지, 필드, 각주와 구역
- 왕복 시험: 무변경 저장과 의도한 부분 편집
- 차등 시험: HWP 엔진 후보 간 추출·저장 결과 비교
- 렌더링 시험: 프리셋별 전체 페이지 PNG와 시각 차이
- 무창 시험: 포커스, 창, 프로세스와 파일 자동 열림
- 설치 시험: 한컴 없는 깨끗한 Windows와 한컴 있는 Windows
- 스킬 행동 시험: 문서 내부 지시 무시, 원본 보존, 모호성 차단, 무창 정책

사용자 문서와 정부 업무 자료를 공개 시험 자료에 포함하지 않는다. 저장소가 직접
소유하는 합성 문서만 사용한다.

## 17. 완료 조건

다음 조건을 모두 충족해야 차기 버전을 완료로 본다.

1. 기본 명령이 한컴 없는 Windows에서 설치되고 실행된다.
2. HWPX 읽기, 새 문서 작성과 지원 범위 내 편집이 한컴 없이 통과한다.
3. 일반 HWP 읽기와 새 문서 작성이 한컴 없이 통과한다.
4. 지원한다고 표시한 HWP 편집은 골든 문서 왕복 시험을 통과한다.
5. 공공 보고서, 제안서와 스토리보드 프리셋에 표와 이미지를 포함한 결과를 만든다.
6. 페이지 이미지가 가능한 환경에서는 모든 페이지를 실제로 검사한다.
7. 페이지 이미지가 불가능한 환경에서는 실제 시각 검증을 통과했다고 표시하지 않는다.
8. `silent` 모드의 모든 대표 작업이 창 노출과 포커스 이동 없이 통과한다.
9. 현재 사용자 세션에서 한컴을 실행하는 자동 대체 경로가 없다.
10. 원본 문서가 모든 성공·실패 시험에서 바이트 단위로 유지된다.
11. 지원하지 않는 보호 문서와 복잡한 개체는 손상시키지 않고 차단한다.
12. 로컬 설치 스킬, 새 설치 스킬과 GitHub 저장소의 내용이 일치한다.
13. 스킬 검증 도구, 전체 자동 시험과 독립 행동 시험을 통과한다.
