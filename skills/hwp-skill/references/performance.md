# 빠른 문서 처리와 간결한 응답

일반 AI 작업에는 `inspect`와 `generate`의 `-ResultDetail compact`를 사용한다.
사용자는 옵션을 외울 필요가 없다. 기존 도구 연동을 위해 CLI 기본값은 `full`이다.
Windows PowerShell에서는 `powershell`, PowerShell 7에서는 `pwsh`로 같은 스크립트를 실행한다.

```powershell
pwsh -NoProfile -File "<스킬 경로>/scripts/Invoke-HwpSkill.ps1" inspect -LiteralPath "원본.hwpx" -ResultDetail compact
pwsh -NoProfile -File "<스킬 경로>/scripts/Invoke-HwpSkill.ps1" generate -NewDocument -PlanPath "계획.json" -OutputPath "별도 결과.hwpx" -ResultDetail compact
```

## 응답 계약

| 작업 | compact에 남는 정보 | 생략한 정보가 필요한 경우 |
| --- | --- | --- |
| 검사 | 본문, 필드, 표의 cells/grid/병합, 문단·run·셀 주소, 원본 SHA-256, 쪽 설정, 저장 줄 배치와 정확도 경고 | `resources` 원문 대신 `resourceSummary`의 리소스별 개수만 제공. 글꼴·서식 정의는 `inspect -ResultDetail full` |
| 새 문서 생성 | 상태·경고·오류, 출력/복구 경로, 작업 결과, 독립 구조 검사, `data.AfterSummary`의 해시·개수·배치 검증 수준 | 본문과 편집 주소는 결과 파일을 `inspect`하여 취득. 이전 전체 응답 구조는 `-ResultDetail full` |

`resultDetail`, `omitted`, `fullResultHint`는 응답 생략 범위를 명시한다. 생성 결과의 중복
최상위 필드는 `data`에 한 번만 제공하며 추가 검증 필드는 유지한다. 검사/생성 이외의
명령과 알려지지 않은 실패 결과는 원래 구조를 유지하고 JSON의 공백만 줄인다.
compact 검사는 서식 리소스가 생략되므로 전체 inspection 스키마/기존 `compare` 입력으로
사용하지 않는다. 전체 검사 비교에는 양쪽 모두 `full`로 저장한다.

경고나 `BLOCKED`를 성공으로 바꾸지 않는다. 특히 최종 HWP 변환기가 없는 경우
`data.WorkingHwpxPath`의 작업본을 보존하지만 요청한 HWP가 완성됐다고 보고하지 않는다.
일반 경로의 종료 코드는 성공 0, 차단 2, 실패 1로 동일하다.

## 속도와 정확도의 경계

명령별 모듈 로딩으로 사용하지 않는 엔진의 시작 비용을 줄인다. 문서 검사 한 번 안에서
요소의 위치를 색인하여 주소마다 앞의 모든 형제를 다시 세지 않는다. 색인은 해당 XML
객체에만 속하며 디스크·전역 캐시로 보관하지 않는다. 색인이 100,000항목을 넘으면
색인을 버리고 기존 주소 계산을 사용해 추가 메모리를 제한한다. 미지 XML을 생략하거나
문서를 새로 거부하지 않는다. 새 파일은 새 해시와 주소로 다시 검사한다. ZIP/XML 한도·
원본 해시·표 경계·재개봉·독립 구조 검사·승격 조건은 생략하지 않는다.

Word 문서도 일반적으로 파일 내부 XML을 직접 작성한 뒤 렌더링해 검토한다. 이 스킬도
HWPX를 직접 기록하지만 원본 HWP 판독·입력 변환·보존 검사와 지원 범위가 다르다.
HWPX의 무창 미리보기는 한컴 조판기가 아닌 근사 경로이므로, 실행 경량화만으로 Word와
같은 작성 속도나 한컴의 글꼴·줄바꿈·인쇄 배치를 보장하지 않는다. 계산하지 않은
`linesegarray`를 복사하거나 가짜 쪽 수를 넣어 빠르게 보이게 하지 않는다.

## 2.10.0 로컬 비교

2026-10-21, 같은 Windows PC의 PowerShell 7.6.5에서 2.9.0 설치본과 새 CLI를
번갈아 각각 3회 실행한 중앙값이다. 새 PowerShell 시작·내부 검증·전체 JSON 반환까지
포함하며 입력은 합성 문서다. Word와의 직접 속도 비교나 전용 성능 시험 장비의 결과가 아니다.

| 작업 | 2.9.0 full | 2.10.0 full | 2.10.0 compact |
| --- | ---: | ---: | ---: |
| 기능 조회 | 1.31초 | 0.62초 | 별도 측정 없음 |
| 빈 문서 검사 | 1.67초 | 1.39초 | 1.41초 |
| 본문 499문단·500셀 검사 | 9.97초 | 5.98초 | 5.84초 |
| 본문 100문단·100셀 생성 | 7.20초 | 6.89초 | 6.92초 |

생성 응답은 full 1,725,661바이트 → compact 2,254바이트, 빈 문서 검사 응답은
344,838 → 8,043바이트였다(UTF-8). compact의 이득은 주로 전달·해석할 데이터량이며
생성·검사 자체가 반드시 full보다 빨라진다는 뜻은 아니다. 상한 보완 전의 독립된 같은 파일
검사 18회는 변경 전 전체 JSON과 정확히 일치했다. 해당 내부 검사만의 대형 표본에서는
약 24~49% 단축됐지만 작은 표본에서는 약 8% 느려지기도 했다. 최종 상한 초과의 기존
계산 복귀도 전체 JSON 동등성과 원본 해시 보존을 별도 검사했다. 병렬 작업·첫 실행의
영향이 있는 소수 로컬 측정이므로 문서 전체에 같은 성능을 약속하지 않는다.
